# 初次打包与部署

在 Linux 打包机上打好交付包，运维拿压缩包到客户环境安装。客户服务器和客户 Jetson 都不放源码。

装完之后发新版本，见 [后续打包与升级.md](后续打包与升级.md)。

## 分工

| 做什么 | 在哪一台机器 | 这台机器上有什么 |
|--------|--------------|------------------|
| 打版本 tag、构建平台镜像、打应用包、导出交付包 | Linux 打包机 | 仓库、Docker |
| 构建边缘镜像并导出 tar | 一台开发用的 Jetson | 仓库、JetPack 6、Docker、NVIDIA Container Runtime |
| 安装管理平台 | 客户服务器 | Docker（含 Compose 插件）、交付包 |
| 安装边缘程序 | 每台客户 Jetson | Docker、NVIDIA Container Runtime、交付包 |

客户机器不需要 Node、Python 或仓库。平台镜像在打包机上打成 Linux amd64，客户服务器用 x86_64。边缘镜像只能在 Jetson 上打。边缘镜像体积大，打包机、拷贝介质和客户盒子都要留足磁盘。

## 1. 创建版本 tag

正式交付使用 Git tag 作为唯一版本来源。先提交本次发布代码，再创建并推送 tag。Linux 打包机和 Jetson 构建机都检出这同一个 tag，不要在 tag 提交上保留未提交修改。

以下以 `v1.0.3` 为例：

```bash
git tag -a v1.0.3 -m "Release v1.0.3"
git push origin v1.0.3
```

Makefile 会从当前提交的精确 `vX.Y.Z` tag 取版本，并检查工作区干净；tag 不存在、格式不符或有未提交修改时会停止。该版本会写入安装包及其中的 `VERSION` 文件，不会改写仓库里的 `backend/VERSION` 或 `edge-agent/VERSION`。运行时镜像和升级器不带这个版本号，初次安装后保持不动。

## 2. Jetson 构建机

只用一台开发用的盒子打镜像。客户现场的盒子不做这一步。这台机器需要能访问外网，以便拉取 `ultralytics/ultralytics:latest-jetson-jetpack6`。`latest` 是可变标签；每次构建应记录实际使用的基础镜像版本，并确认它适配目标设备的 JetPack。

在仓库根目录取出第 1 节推送的 tag。工作区保持干净。默认构建会使用 `requirements.txt`，安装通用依赖；Ultralytics 和 Torch 由基础镜像提供。`requirements-jetson.txt` 不会被默认选中。镜像打好后，以后只改应用代码可以复用；Dockerfile、依赖或基础镜像变更时必须重新构建。

```bash
git fetch origin tag v1.0.3
git checkout v1.0.3
cd edge-agent
docker compose build
docker save -o sjic-edge-jetson.tar sjic-edge:jetson
```

示例 tag 应替换为本次发布 tag。把 `sjic-edge-jetson.tar` 拷回 Linux 打包机，放在仓库根目录。边缘依赖没变时，以后打 setup 包可以继续用这份 tar。

构建后先检查镜像内 OpenCV 的视频后端：

```bash
docker run --rm --entrypoint python sjic-edge:jetson -c "import cv2; s=cv2.getBuildInformation(); i=s.find('Video I/O:'); print(s[i:s.find('\n\n', i)])"
```

若输出 `GStreamer: NO`，该镜像就不能通过 OpenCV 的 GStreamer 后端使用 Jetson `nvv4l2decoder`；RTSP 会回退到 FFmpeg，不能据此认为 NVDEC 正在工作。当前 Dockerfile 安装的 `opencv-python-headless` 可能提供不含 GStreamer 的 OpenCV。只有显示 `GStreamer: YES`，并在目标设备上实际成功打开 NVDEC 管道后，才能把该镜像视为支持这条硬解路径。requirements-jetson.txt 本身也不会解决 OpenCV 缺少 GStreamer 的问题。

## 3. Linux 打包机

打包和导出都在 Linux 上做。边缘镜像仍用第 2 节拷回来的 tar，不在这台机器上构建。

检出同一个 tag：

```bash
git fetch origin tag v1.0.3
git checkout v1.0.3
```

### 3.1 导出交付包

确认 `sjic-edge-jetson.tar` 已在仓库根目录后执行：

```bash
make release
```

该命令会构建平台运行时镜像、打两个应用安装包，并导出 setup 交付包。导出时只确认边缘 tar 里是 `sjic-edge:jetson`，不要求镜像版本和应用版本相同。默认边缘镜像路径为仓库根目录下的 `sjic-edge-jetson.tar`；也可指定：

```bash
make release EDGE_IMAGE=/path/to/sjic-edge-jetson.tar
```

`dist/` 里会有这些文件：

| 文件 | 用途 |
|------|------|
| `sjic-platform-setup-<版本>.tar.gz` | 交给运维，装到客户服务器 |
| `sjic-edge-setup-<版本>.tar.gz` | 交给运维，装到每台客户 Jetson |
| 同名的 `.sha256` | 和对应 setup 包一起交给运维，拷贝后核对 |
| `sjic-platform-<版本>.tar.gz`、`sjic-edge-<版本>.tar.gz` | 应用包，已经打进上面的 setup 包。初次安装不要单独把这两个文件交给运维 |

例如 tag 为 `v1.0.3` 时，文件名中的版本是 `1.0.3`。应用包里是 Python 字节码和前端页面，没有 `.py` 源码。

运维拿到文件后先核对：

```bash
sha256sum -c sjic-platform-setup-1.0.3.tar.gz.sha256
sha256sum -c sjic-edge-setup-1.0.3.tar.gz.sha256
```

## 4. 部署：客户管理平台

客户服务器先装 Docker 和 Compose 插件：

```bash
sudo apt install docker.io docker-compose-v2
docker compose version
```

`docker compose version` 能打出版本号后再继续。把 `sjic-platform-setup-<版本>.tar.gz` 拷到客户服务器后执行（以下以 `1.0.3` 为例）：

```bash
sha256sum -c sjic-platform-setup-1.0.3.tar.gz.sha256
tar -xzf sjic-platform-setup-1.0.3.tar.gz
cd sjic-platform-setup-1.0.3
sudo bash install.sh
```

脚本会导入镜像，把应用放到 `/opt/sjic/releases/1.0.3`，执行数据库迁移，启动容器，并启用升级服务 `sjic-updater`。镜像和升级器就在这一步固定下来。

后端第一次启动时随机生成 JWT 签名密钥，保存在 `/opt/sjic/data/instance/secret_key`。不要删除这个文件，删除后所有人都要重新登录。

浏览器打开 `http://<服务器IP>:38880`。客户 Jetson 要能访问下面三个端口。

| 端口 | 用途 |
|------|------|
| 38880 | 页面，以及边缘下载模型、安装包 |
| 38881 | API |
| 38883 | MQTT。边缘心跳、任务下发、升级指令 |

出厂账号：

| 用户名 | 密码 | 角色 |
|--------|------|------|
| super_admin | 123123 | 服务商 |
| admin | 123123 | 客户 |

交付前在页面改掉这两个密码。未导入授权时可以登录，业务功能不可用。在「授权管理」复制机器码，签发后导入。说明见 [backend/docs/LICENSE_DEPLOYMENT.md](../backend/docs/LICENSE_DEPLOYMENT.md)。授权绑定宿主机 `/etc/machine-id`，重建容器不会使授权失效。

## 5. 部署：客户 Jetson

每台客户盒子做一次。盒子要能访问管理平台的 `38880`、`38881`、`38883`。镜像已经在交付包里，现场不用拉取基础镜像。

确认 Docker、Compose 插件和 NVIDIA 运行时：

```bash
docker compose version
docker info | grep -i -A2 Runtimes
```

`Runtimes` 里需要有 `nvidia`。没有的话先安装 NVIDIA Container Toolkit 并重启 Docker，再执行安装脚本。

解压后先改 `config.yaml.example` 里的平台地址：

```yaml
architecture: "jetson"

mqtt:
  broker_url: "管理平台IP"
  broker_port: 38883

platform:
  api_base_url: "http://管理平台IP:38881/api/edge"
```

`edge_name` 留空时使用主机名。

```bash
sha256sum -c sjic-edge-setup-1.0.3.tar.gz.sha256
tar -xzf sjic-edge-setup-1.0.3.tar.gz
cd sjic-edge-setup-1.0.3
sudo bash install.sh
```

脚本把示例配置复制到 `/opt/sjic/edge/config.yaml`（这个文件已存在则不覆盖），导入镜像并启动 `sjic-edge`，等程序完成初始化后才返回。最多等 3 分钟；超时说明程序起不来，用下面的命令看日志。

安装时还没改地址的话，之后编辑 `/opt/sjic/edge/config.yaml`，再执行：

```bash
docker restart sjic-edge
```

看日志：

```bash
docker logs -f sjic-edge
```

出现心跳后，管理平台按本机 MAC 登记该节点。

## 6. 装完后的目录

管理平台：

```text
/opt/sjic/current -> /opt/sjic/releases/1.0.3
/opt/sjic/updater/          升级器与现场 compose
/opt/sjic/data/             数据库、模型、告警等
/opt/sjic/data/instance/    数据库、JWT 密钥，backups/ 里是每次升级前的数据库备份
/opt/sjic/data/data/        区域配置、图片测试样本，images/ 里是标定图片
```

Jetson：

```text
/opt/sjic/current -> /opt/sjic/releases/1.0.3
/opt/sjic/edge/config.yaml
/opt/sjic/edge/models|alerts|logs
```

数据库、模型、告警、录像和边缘配置在后续升级时保留。镜像和升级器保持这次装上的内容。

下一版在 Linux 打包机上执行 `make package`，把两个应用包拿到页面上传。见 [后续打包与升级.md](后续打包与升级.md)。
