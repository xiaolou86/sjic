# 后续打包与升级

现场已经按 [初次打包与部署.md](初次打包与部署.md) 装过一次之后，用这份流程发新版本。运行时镜像和升级器保持初次安装的那一份，不随应用版本更换。

升级只替换 `/opt/sjic/current` 指向的应用目录，不覆盖数据库、模型、告警、录像和边缘的 `config.yaml`。在 Linux 打包机上打包即可，不用再上 Jetson，也不要重新构建镜像。

| 谁 | 在哪 | 做什么 |
|----|------|--------|
| 开发 | Linux 打包机 | 打 `dist/sjic-platform-<版本>.tar.gz` 和 `dist/sjic-edge-<版本>.tar.gz`，交给运维 |
| 运维 | 客户管理平台的页面 | 上传这两个包。平台包在本机升级，边缘包到「节点」页按台下发 |

客户机器上没有仓库，也不要再解压 setup 交付包。安装包在 Linux 打包机上打，本机不用安装 Python 或 Node。

## 1. 打包

每个正式版本都从一个干净的 `vX.Y.Z` Git tag 构建。在 Linux 打包机上检出该 tag。Makefile 会从 tag 自动取版本，禁止在 tag 提交有未提交更改时打包。打包容器自带 Python 3.10 和 Node，字节码必须和现场解释器一致。

```bash
git fetch origin tag v1.0.4
git checkout v1.0.4
make package
```

默认打两个应用包。如果只打一个，在仓库根目录执行 `make package COMPONENT=platform` 或 `make package COMPONENT=edge`。

产物在 `dist/`：

| 文件 | 上传位置 |
|------|----------|
| `sjic-platform-<版本>.tar.gz` | 系统设置 → 上传平台包 |
| `sjic-edge-<版本>.tar.gz` | 系统设置 → 上传边缘包 |

包内是 `.pyc`、前端 `build`、`install.sh` 和 `manifest.json`，没有 `.py` 源码。清单里登记每个文件的 SHA256，上传和安装时都会核对。版本号写进包内 `VERSION`。最低可升级版本默认 `1.0.0`。

包里只收运行需要的文件，白名单在 `deploy/build_release.py` 的 `PLATFORM_ENTRIES`、`EDGE_ENTRIES`。代码新增顶层文件或目录时要加进去。`config.yaml`、测试、调试脚本和文档不进包。仓库里如果有 `.bak`、视频、数据库这类文件，打包会直接报错。

打包容器会在仓库里执行前端构建，`frontend/build` 会被更新。这是安装包的前端，不是现场页面目录。

## 2. 升级管理平台

用客户或服务商账号登录。授权有效后，「系统设置」里才能上传和升级。

升级前先到「任务」里停掉所有运行中的任务。有任务在运行时，平台会拒绝升级并列出这些任务。手动停止的定时任务不会再被自动拉起，升级完成后要手动启动一次。

1. 打开「系统设置」。
2. 点「上传平台包」，选择 `sjic-platform-<版本>.tar.gz`。页面提示「安装包已校验」后，状态行会出现已上传的版本号。安装包版本低于当前版本时会被拒绝：数据库只能往前迁移，平台不支持降级。同一版本可以重装。
3. 点「升级本机」，确认。

页面会短暂打不开。宿主机升级器只校验安装包并解压，然后执行包里的 `install.sh`。校验规则固定在升级器里。切换目录、迁移和回滚在 `install.sh` 里，随应用包更新，不用改升级器。`install.sh` 会：

1. 检查磁盘剩余空间，至少要有数据库大小加 1 GB。不够就直接报失败，不做任何改动。
2. 停止 `sjic-backend`，把 `app.db` 连同 `app.db-wal` 备份到 `/opt/sjic/data/instance/backups/<时间>-<旧版本>/`。
3. 把旧版本目录里现场生成的标定图片等文件拷到 `/opt/sjic/data/data/images`，已有的不覆盖。
4. 解压到 `/opt/sjic/releases/<版本>`，把 `/opt/sjic/current` 指过去。
5. 用新版本起一个一次性容器执行数据库迁移。
6. 重建 `sjic-backend`、`sjic-frontend` 容器（仍用原来的运行时镜像）。
7. 请求 `/api/health`，确认返回的版本号与安装包一致。
8. 成功后只保留当前版本和最近 2 个旧版本目录，以及最近 3 份数据库备份。

任一步失败时，自动停容器，恢复备份的数据库，切回上一版目录并启动。系统设置里的平台状态会变成失败，并带原因。

从没有这些检查的旧版本升到这一版时，旧平台还不会拦截运行中的任务，要先手动全部停止。升级后所有人需要重新登录一次：JWT 签名密钥改为在现场随机生成，保存在 `/opt/sjic/data/instance/secret_key`。

升级过程中不要在服务器上再执行 `docker compose build` 或仓库根目录的 `docker compose up`。现场编排文件是 `/opt/sjic/updater/docker-compose.yml`。

看升级器日志：

```bash
journalctl -u sjic-updater -f
cat /opt/sjic/current/VERSION
```

## 3. 升级 Jetson

边缘包先上传到管理平台，再按台下发。不要在盒子上重新 `docker compose build`。先升平台，再升边缘。

下发前平台会检查：节点在线；该节点上没有运行中的任务；边缘包版本不高于平台当前版本。不满足时拒绝下发并说明原因。

1. 在「系统设置」点「上传边缘包」，选择 `sjic-edge-<版本>.tar.gz`，等到校验通过。
2. 在「任务」里停掉该节点上运行中的任务。
3. 打开「节点」，确认目标在线。
4. 对该节点选择「升级程序」。菜单会显示即将安装的版本；没有已上传的边缘包时不能下发。

盒子收到指令后：

1. 再查一次本机有没有任务在运行，有就拒绝。升级期间不接受新任务；定时任务会在升级完成后由平台自动补启动。
2. 从管理平台 `38880` 下载安装包并核对校验和。只接受管理平台地址的安装包。
3. 宿主机脚本校验清单后，把后续步骤交给宿主机 systemd 执行（单元名 `sjic-edge-upgrade`）。不这样做，重建容器时会把升级脚本一起停掉。
4. 检查磁盘至少剩 500 MB，切换 `/opt/sjic/current`，重建 `sjic-edge`。
5. 新版本启动后写出 `/opt/sjic/incoming/edge.ready`。3 分钟内等不到，就切回上一版，节点上报失败原因。
6. 成功后只保留当前版本和最近 2 个旧版本目录。

`/opt/sjic/edge/config.yaml`、模型、告警、日志保持不变。节点卡片上会显示升级状态。

在盒子上看升级过程：

```bash
journalctl -u sjic-edge-upgrade
cat /opt/sjic/incoming/edge.status.json
cat /opt/sjic/current/VERSION
```

## 4. 版本与失败

- 版本号从当前精确的 Git tag 读取，例如 tag `v1.0.3` 生成版本 `1.0.3`。同一版本再次上传会覆盖平台上暂存的那个包。
- 现场当前版本低于包里的最低版本时，校验直接失败，不会切换目录。
- 平台升级同一时间只能有一个。状态还是「等待升级器」或「正在升级」时，不要重复点「升级本机」。
- 平台不能降级。边缘可以：上传旧版本的边缘包再下发即可。只能退回到包含 `systemd-run` 升级方式的版本，更早版本的安装脚本可能在重建容器时中断。
- 授权无效时，上传和升级按钮不可用。
- 应用包换不了镜像里的 pip 包、系统包，也换不了 `/opt/sjic/updater`。这两样在初次安装时定下来。Dockerfile、依赖或升级脚本本身要改时，才按初次文档重新打 setup 包，到现场再执行一次 `install.sh`。已经装过的机器不会覆盖应用、数据库和边缘配置。

## 5. 手工回滚

升级成功后发现业务问题，或后端起不来、页面进不去时，在服务器上手工切回。回滚会丢掉备份之后写入的数据。

管理平台：

```bash
ls -lt /opt/sjic/releases /opt/sjic/data/instance/backups
cd /opt/sjic/updater
docker compose stop backend
B=/opt/sjic/data/instance/backups/<时间>-<旧版本>
rm -f /opt/sjic/data/instance/app.db-wal /opt/sjic/data/instance/app.db-shm
cp -a "$B/app.db" /opt/sjic/data/instance/app.db
if [ -f "$B/app.db-wal" ]; then cp -a "$B/app.db-wal" /opt/sjic/data/instance/app.db-wal; fi
ln -sfn /opt/sjic/releases/<旧版本> /opt/sjic/current
docker compose up -d --force-recreate backend frontend
```

Jetson 没有数据库，只切目录：

```bash
ln -sfn /opt/sjic/releases/<旧版本> /opt/sjic/current
docker compose -f /opt/sjic/updater/docker-compose.yml up -d --force-recreate edge-agent
```

## 6. 和初次部署的差别

| | 初次 | 后续 |
|--|------|------|
| 运行时镜像 | 打进 setup 交付包，现场 `docker load`，之后保持不动 | 继续用原镜像 |
| 升级器 | 写入 `/opt/sjic/updater`，之后保持不动 | 继续用原来的升级器 |
| 应用代码 | setup 包里的应用包 | 页面上传的应用包 |
| 谁执行 | 运维在客户机器执行 `install.sh` | 页面上传；平台由 `sjic-updater` 执行，边缘由平台下发 |
